## 한 줄 정의
AC = Acceptance Criteria(인수 조건). **"무엇이 되면 완료인가"를 검증 가능한 문장으로 쪼갠 뒤, 큰 조건 아래 작은 조건을 매다는 계층 구조**.

## 자세히
인수 조건 자체는 애자일에서 오래된 개념이다. 사용자 스토리 하나에 "이게 만족되면 받아들이겠다"는 조건을 붙여, 완료(done)의 판단을 주관이 아니라 합의된 문장에 맡긴다. 핵심은 **검증 가능성**이다. "로그인이 잘 된다"는 AC가 아니고, "올바른 자격증명으로 POST /login 하면 200과 세션 쿠키를 받는다"는 AC다.

트리로 만드는 이유는 크기 때문이다. 실제 요구사항은 한 문장으로 검증하기엔 너무 크고, 잘게 쪼개기만 하면 왜 필요한지가 사라진다. 그래서 큰 AC(사용자가 체감하는 기능) 밑에 작은 AC(그걸 성립시키는 세부 동작)를 매단다. 부모는 "왜"를, 자식은 "어떻게 확인하나"를 담당한다.

[Ouroboros](/posts/ouroboros-usage/)에서 AC 트리는 [Seed 스펙](/posts/seed-spec/)의 핵심 구성 요소이자 **진행률 추적의 단위**다. 각 AC는 `pending` → `in_progress` → `passed` / `failed` 상태를 갖고, 실행기는 AC를 태스크로 분해해 처리한다. 그래서 "지금 몇 % 됐나"가 느낌이 아니라 통과한 AC 수로 나온다.

평가 단계에서도 기준이 된다. 3단 평가 중 2단(의미적 평가)이 보는 게 바로 **AC 준수 여부**다. 여기서 중요한 함의가 하나 나온다 — AC가 모호하면 검증도 모호해진다. "성능이 좋아야 한다"는 AC를 넣으면 통과 여부를 아무도 판정할 수 없고, 결국 채점이 무의미해진다. AC 트리의 품질이 곧 [결정화](/posts/crystallization/) 품질이고, [소크라테스 인터뷰](/posts/socratic-interview/)가 캐물어야 하는 대상도 정확히 이 지점이다.

## 예시
```
AC-1  "사용자가 할 일을 추가할 수 있다"                   [passed]
├─ AC-1.1  "todo add <text> → ~/.todo.json 에 append"    [passed]
├─ AC-1.2  "빈 문자열 입력 시 에러 메시지 + exit code 1"  [in_progress]
└─ AC-1.3  "추가된 항목에 순번 id 부여"                   [passed]

AC-2  "완료 항목을 목록에서 감출 수 있다"                 [pending]
├─ AC-2.1  "todo done <id> → archived=true"              [pending]
└─ AC-2.2  "todo list 는 archived 항목 제외"             [pending]

진행률 = passed 3 / 전체 7
```
나쁜 AC와 좋은 AC:
```
✗  "빠르게 동작해야 한다"            → 판정 불가
○  "1만 건 목록 조회가 200ms 이내"   → 판정 가능
```
