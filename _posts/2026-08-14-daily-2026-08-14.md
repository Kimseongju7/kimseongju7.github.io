## 요약

geul-hub 뷰어 버그를 마무리하고 홈 화면을 갈아엎은 날. 어제 남겨 둔 피드백 클릭 씹힘을 도커부터 다시 띄워 재현했는데 원인이 예상과 달랐다 — 빠른 클릭은 480회를 두들겨도 멀쩡했고, **문서를 열자마자(텍스트 레이어가 아직 그려지는 중) 클릭할 때만** 17% 씹혔다. 실패했을 때만 1회 재시도하는 최소 수정으로 0/532 까지 잡아 PR #208 로 머지했다.

중간에 사고가 하나 있었다. 테스트가 진행 중인데 새 작업 브랜치를 파는 바람에 dev 서버가 수정 전 코드를 서빙해 고친 게 전부 화면에서 사라졌고, 그래서 순서를 **검증 끝난 수정 먼저 머지 → 새 브랜치는 최신 develop 에서** 로 바꿨다. 이어서 홈을 폴더 없이 문서만 최근 수정순으로 다시 짜고, BE 가 넣어 준 `viewPdfUrl` 로 썸네일 N+1 까지 없애 PR #209 로 머지했다(805 테스트 그린). 토익은 문법형 문제를 푸는 순서를 잡았다.

**[geul-hub] 피드백 클릭 씹힘 버그 — 진짜 원인은 "빠른 클릭"이 아니었다**

- ✨ 어제 중단했던 씹힘 버그를 도커부터 다시 띄워 재개했다(Docker Desktop 기동 → postgres·백엔드 컨테이너 start → 헬스 200). 어제 확보해 둔 코드 분석(무음 실패 확정·마크 공백 시간창 확정·경계 오프셋 후보)과 프로브 설계를 그대로 들려 재현 → 원인 확정 → 최소 수정 → 재검증 순서로 진행했다.
- ✨ 재현 프로브 결과가 가설을 뒤집었다. **정상 상태에서는 50ms 간격으로 480회를 두들겨도 0번 씹혔고**, 씹힘은 오직 **문서를 열자마자(텍스트 레이어가 아직 그려지는 중) 클릭할 때만** 17% 확률로 발생했다. 그 순간엔 문서 텍스트 DOM 이 통째로 비어 있어 이동 대상을 찾지 못하는데, 실패를 알리지도 재시도하지도 않아 무음으로 사라진 것.

## 배운 것

<!-- claude-recall-learn:rlatjdwn:start -->

**재현 프로브는 가설을 확인하는 게 아니라 반증하는 데 쓴다**

- ✨ "빠른 클릭이 씹힌다"는 체감 가설로 시작했지만, 프로브를 돌리니 50ms × 480회에 0번 씹혔다. 대신 조건을 갈라 측정하자 **초기 렌더 중 클릭에서만 17%** 라는 전혀 다른 그림이 나왔다. 수치 없이 체감으로 원인을 확정했다면 엉뚱한 곳(클릭 스로틀링·이벤트 큐)을 고쳤을 것이다. 조건별로 나눠 재현율을 숫자로 뽑는 게 원인 판정의 출발점이다.

**무음 실패는 그 자체가 버그다**

- ✨ 이번 씹힘의 본질은 "DOM 에 대상이 없어서 이동 실패"가 아니라 **실패를 알리지도, 재시도하지도 않고 조용히 사라진 것**이었다. 대상이 아직 없을 수 있는 비동기 렌더 환경에서는 즉시 실패를 정상 흐름의 일부로 다뤄야 한다 — 실패했을 때만 대상이 나타나는 순간을 관찰해 1회 재시도하고, 상한(5초)과 취소(새 요청이 오면 이전 예약 파기)를 붙이는 식으로. **성공 경로는 손대지 않는 게 핵심**이라 회귀 위험이 거의 없다.

**남이 앱을 테스트하는 중에 브랜치를 갈아타면 안 된다**

- ✨ dev 서버는 작업 트리를 그대로 서빙하므로, 브랜치 전환은 곧 **보고 있는 화면의 롤백**이다. 수정한 게 사라지면 "재발"로 오인되고 디버깅이 헛돈다. 순서를 바꾸는 게 답이다 — 검증 끝난 수정은 **먼저 머지해 develop 에 태운 뒤** 새 작업 브랜치를 최신 develop 에서 파면, 이후 어떤 브랜치로 옮겨도 화면이 되돌아가지 않는다.

**"최근"에는 두 가지가 있다 — 접근 순과 수정 순**

- ✨ 홈을 "최근 순"으로 만들려고 기존 `recent-items` API 를 쓰려다 확인해 보니 그건 **열람 기록 기반(최근 접근)** 이었다. 요구는 **최근 수정순 문서 목록**이라 의미가 다르고, 카드 렌더에 필요한 필드도 없었다. 이름이 비슷한 기존 API 를 재사용하기 전에 그 API 가 어떤 이벤트를 기준으로 정렬하는지, 화면이 필요로 하는 필드를 다 갖고 있는지부터 계약으로 확인해야 한다.

**FE 의 N+1 은 BE 계약을 바꿔야 사라진다**

- ✨ 카드마다 썸네일을 얻으려고 버전 목록을 따로 부르던 N+1 은 프론트 최적화로 줄일 수 있는 게 아니라, **목록 응답에 필요한 필드(`viewPdfUrl`)를 넣어 달라는 계약 변경**으로만 근본 해결됐다. 그래서 이슈(#202 → #206)로 넘겨 두고, 필드가 들어온 뒤 요청 자체를 삭제하는 순서가 맞다. 같은 화면의 `latestUploadedBy` 도 똑같은 모양이지만 필드가 없어 **아직 남아 있는 별개 건**이다 — 하나 고쳤다고 같은 패턴이 다 없어진 게 아니라는 걸 목록 계약 기준으로 다시 훑어야 한다.

**토익 Part 5 — 문법형 문제는 동사의 개수부터 센다**

- 보기가 **동사와 동사가 아닌 것**으로 섞여 있는 문법 문제라면, 우선 문장에서 **동사의 개수**를 봐야 한다. 동사의 개수 = **접속사 + 1** 이다.
- 빈칸이 동사 자리라고 판단되면 **수일치 → 능동/수동태 → 시제** 순으로 보면서 보기를 소거해 나간다.
- 답을 고를 때 **해석은 확인 절차로** 쓴다 — 확신이 서지 않을 경우에.
