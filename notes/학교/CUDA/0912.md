# 0912 CUDA — 비동기와 CUDA 스트림

> 교재: NVIDIA DLI 「최신 CUDA C++를 사용한 가속 컴퓨팅의 기초」 slide2.pdf (2부)
> 관련: [[0905 - slide1]] · [[Thrust 개요]]

이번 장의 목표는 하나다. **GPU가 일하는 동안 CPU도 놀지 않게 만드는 것.**
세 단계로 올라간다 — ① 비동기(계산 ↔ IO 겹치기) → ② 스트림(계산 ↔ 메모리 전송 겹치기) → ③ Pinned 메모리(전송을 진짜 비동기로).

---

## 1. 문제 — 유휴 리소스

기존 코드의 한 스텝은 이렇게 생겼다.

- **쓰기 단계** : 이전 상태를 CPU로 복사하고 디스크에 쓴다
- **계산 단계** : 이전 상태를 읽고 다음 상태를 쓰는 `thrust::tabulate`

Thrust는 내부적으로 **동기식**이다. GPU에서 작업을 시작하고 **완료될 때까지 기다린다.**
그동안 CPU는 아무것도 안 한다. 이기종(heterogeneous) 프로그램을 잘 쓴다는 건 CPU를 포함한 모든 수단을 쓴다는 뜻인데, 지금은 절반이 논다.

**그런데 두 단계 사이에는 데이터 종속성이 없다.**

| 단계 | 읽는 것 |
|---|---|
| 쓰기 | 이전 상태의 **호스트** 복사본 |
| 계산 | 이전 상태의 **디바이스** 복사본 |

서로 다른 메모리를 읽으므로 순서를 지킬 이유가 없다. → **CPU가 디스크에 쓰는 동안 GPU가 계산하면 된다.**
단, 그러려면 Thrust 호출을 "시작"과 "기다림"으로 쪼갤 수 있어야 한다.

## 2. CUB — Thrust 아래 계층

CUDA 코어 라이브러리(CCCL)의 스택은 `Application → Thrust · CUB · libcu++ → CUDA Runtime`이다.
Thrust 호출은 결국 **CUB**를 부른다. ([[Thrust 개요]]의 스택 그림)

```
Sorting                     Iterators                            Types
cub::DeviceTransform        cub::CacheModifiedInputIterator      cub::FutureValue
cub::DeviceRadixSort        cub::CacheModifiedOutputIterator     cub::DoubleBuffer
```
<https://nvidia.github.io/cccl/cub>

**핵심 차이 : Thrust는 동기, CUB는 비동기.**
CUB는 제어 흐름이 알고리즘 완료를 기다리지 않는다. Thrust가 동기처럼 보이는 이유는 내부에서 `cudaDeviceSynchronize`를 부르기 때문이다.

### 비동기라는 게 눈에 보이는 방식

```cpp
// Thrust — 동기
auto begin = std::chrono::high_resolution_clock::now();
thrust::tabulate(thrust::device, out.begin(), out.end(), compute);
auto end   = std::chrono::high_resolution_clock::now();

// CUB — 비동기
auto begin = std::chrono::high_resolution_clock::now();
auto cell_ids = thrust::make_counting_iterator(0);
cub::DeviceTransform::Transform(cell_ids, out.begin(), num_cells, compute);
auto end   = std::chrono::high_resolution_clock::now();
```

CUB 쪽 경과 시간은 **문제 크기(16M → 67M → 268M)를 키워도 늘지 않는다.**
빠른 게 아니라 **아직 안 끝났는데 시간을 찍은 것.** CPU는 변환이 끝나길 기다리지 않고 다음 줄로 갔다.

### 명시적 동기화

```cpp
cub::DeviceTransform::Transform(cell_ids, out.begin(), num_cells, compute);
cudaDeviceSynchronize();          // ← 이걸 넣으면 Thrust와 같은 곡선이 나온다
auto end = std::chrono::high_resolution_clock::now();
```

`cudaDeviceSynchronize`
- CUDA 런타임의 일부
- **GPU에 대한 모든 작업**이 완료될 때까지 블록
- CUB 버전도 동기식으로 만든다

## 3. Compute-IO 중복 (연습 02.02.02)

요령은 하나다. **`cudaDeviceSynchronize`를 디스크 쓰기 *뒤에* 둔다.**

```cpp
thrust::copy(dprev.begin(), dprev.end(), hprev.begin());

for (int step = 0; step < steps; step++)
{
    simulate(height, width, dprev, dnext);   // 내부는 CUB → 즉시 반환
    dprev.swap(dnext);
}

store(write, height, width, hprev);          // ← CPU가 디스크에 쓰는 동안
cudaDeviceSynchronize();                     // ← GPU는 계속 계산 중
```

```cpp
void simulate(int width, int height,
              const thrust::device_vector<float> &in,
                    thrust::device_vector<float> &out)
{
  auto cell_ids = thrust::make_counting_iterator(0);
  cub::DeviceTransform::Transform(cell_ids, out.begin(), width * height, compute);
}
```

> 시뮬레이션에 IO를 완전히 덮을 만큼의 계산량이 있어서, **거의 2배** 빨라진다.

`thrust::tabulate` → `cub::DeviceTransform::Transform` 치환 시 인자 모양이 바뀌는 점에 주의.

| | Thrust | CUB |
|---|---|---|
| 입력 | 실행 정책 + `out.begin()`, `out.end()` | `counting_iterator` (인덱스 생성) |
| 크기 | 구간 `[first, last)`로 암묵 | `num_items`를 **명시** |
| 반환 | 완료 후 | **즉시** |

## 4. Nsight Systems — 눈으로 확인하기

- GPU와 CPU 활동을 **시스템 전체 타임라인**으로 보여준다
- 비동기 계산·메모리 전송이 시각적으로 드러나므로 **최적화 기회를 눈으로 찾을 수 있다**

사용 흐름
1. `nsys profile` 로 앱을 프로파일링하고 리포트 파일 저장
2. "Connect to Nsight Tool UI" 클릭 (NVIDIA Nsight 탭) — 서버 연결에서 막히면 페이지 새로고침
3. File → Open… 으로 저장한 리포트 열기
4. 시간 영역을 드래그 선택 → **"Filter and Zoom in"**
5. **"CUDA HW"** 를 펼치면 GPU가 실제로 뭘 하고 있었는지 보인다

타임라인에서 확인할 네 가지 — GPU 연산이 **시작되는 시점**, CPU가 디스크에 **쓰는 시점**, CPU가 GPU를 **기다리는 시점**, 데이터가 **전송되는 시점**.

관찰 결과

| | CPU 타임라인 |
|---|---|
| 동기(Thrust) | `copy` 하나로 길게 막혀 있음 |
| 비동기(CUB) | `launch`(짧음) → `wait` |
| + 쓰기 이동 | `launch` → `write` → `wait` — **write가 GPU 계산과 겹침** |

### NVTX

복잡한 앱의 Nsight 리포트는 읽기 부담스럽다. **NVTX**로 코드에 직접 구간 이름을 붙인다.

```cpp
int main()

```

복사 / 계산 / 쓰기 / 대기 단계에 각각 붙여 두면 타임라인에서 단계를 바로 찾을 수 있다.

## 5. CUDA 스트림

여기까지 오면 새 병목이 보인다. **계산이 복사가 끝나길 불필요하게 기다린다.**
복사도 비동기로 만들 수 있다 — `cudaMemcpyAsync`.

### 5.1 `cudaMemcpyAsync`

```cpp
cudaError_t cudaMemcpyAsync(
  void*           dst,     // 목적지 주소
  const void*     src,     // 원본 주소
  size_t        count,     // 복사할 바이트 수
  cudaMemcpyKind kind      // HostToHost / HostToDevice / DeviceToHost / DeviceToDevice
);
```

`thrust::copy` 뒤에 숨어 있던 실체가 이것이다. 대신 날것이라 주의할 점이 있다.

- **타입 안전하지 않다** (`void*`)
- **요소가 아니라 바이트 단위** — `num_cells * sizeof(float)`
- **복사 방향을 명시**해야 한다
- **비동기 오류는 놓치기 쉽다** — 반환된 `cudaError_t`가 *이 호출*의 에러가 아니라 **이전의 비동기 작업**에서 난 에러일 수 있다

### 5.2 스트림이란

- 이 설정만으로는 `cudaMemcpyAsync`가 속도를 못 올린다. **제출된 모든 연산이 GPU에서 순서대로 진행**되기 때문
- GPU에 대한 이런 **작업 순서(queue)** 를 `cudaStream`이라 한다
- 스트림을 지정하지 않으면 **기본 스트림**을 쓴다
- **스트림은 여러 개 만들 수 있고, 서로 다른 스트림의 작업은 동시에 실행될 수 있다**

```cpp
cudaStream_t copy_stream, compute_stream;

// Ⅰ 생성
cudaStreamCreate(&compute_stream);
cudaStreamCreate(&copy_stream);

// Ⅲ 동기화 — 그 스트림의 이전 명령이 모두 끝날 때까지 대기
cudaStreamSynchronize(compute_stream);   // 전체 GPU 동기화보다 가볍다
cudaStreamSynchronize(copy_stream);

// Ⅱ 파괴
cudaStreamDestroy(compute_stream);
cudaStreamDestroy(copy_stream);
```

대부분의 비동기 CUDA 라이브러리가 `cudaStream_t`를 마지막 인자로 받는다.

| 라이브러리 | 시그니처 꼬리 |
|---|---|
| CUDA Runtime | `cudaMemcpyAsync(..., cudaMemcpyKind kind, cudaStream_t stream = 0)` |
| CUB | `cub::DeviceTransform::Transform(..., TransformOp op, cudaStream_t stream = 0)` |
| cuBLAS | `cublasLtMatmul(..., cudaStream_t stream)` |

겹칠 수 있는 대상은 셋 — **메모리 전송**, **호스트 측 계산/IO**, **다른 디바이스 측 계산**.

## 6. 데이터 경합 (중요)

스트림을 나눠 쓴 첫 버전은 이렇게 된다.

```cpp
cudaMemcpyAsync(hprev_ptr, dprev_ptr, num_cells * sizeof(float),
                cudaMemcpyDeviceToHost, copy_stream);   // ① copy_stream에서 D2H 시작

for (int step = 0; step < steps; step++)
{
  simulate(width, height, dprev, dnext, compute_stream); // ② compute_stream에서 계산
  dprev.swap(dnext);
}

cudaStreamSynchronize(copy_stream);      // 호스트 벡터를 읽기 전에 복사 완료 대기
store(write_step, height, width, hprev);
cudaStreamSynchronize(compute_stream);   // 다음 스텝 시작 전에 계산 완료 대기
```

**이 코드에는 데이터 경합이 있다.**
다른 스트림은 순서를 보장하지 않는다 — ①이 `dprev`를 읽는 도중에 ②가 `dprev`를 덮어쓸 수 있다.
(같은 스트림 안의 작업만 순서대로 실행된다.)

### 해법 — 간접 참조 한 겹 (스테이징 버퍼)

> 대부분의 문제는 다른 수준의 간접 참조로 해결할 수 있다.

1. **디바이스 버퍼**를 하나 할당한다
2. **compute stream에서** `dprev` → `dbuffer`로 복사한다 (D2D)
3. **그 버퍼에서** 호스트로 비동기 복사(D2H)를 시작한다

```cpp
thrust::copy(d_prev.begin(), d_prev.end(), d_buffer.begin());   // D2D, 동기
cudaMemcpyAsync(thrust::raw_pointer_cast(htemp.data()),
                thrust::raw_pointer_cast(dbuffer.data()),
                num_cells * sizeof(float), cudaMemcpyDeviceToHost,
                copy_stream);                                   // D2H, 비동기
```

**D2D 복사는 D2H에 비해 오버헤드가 거의 없다.** 한 겹 늘려도 손해가 아니다.

그런데 프로파일링해 보면 아직 문제가 남아 있다 — **복사가 끝나기 전에는 변환이 시작되지 않는다.**

## 7. Pinned 메모리

### 왜 아직 안 겹치는가

- 가상 메모리는 **페이지** 단위다
- **lock(pin) 되지 않은 페이지는 언제든 디스크로 밀려날 수 있다**
- **GPU는 Pinned 메모리에서만 읽을 수 있다**

그럼 pageable 메모리를 대상으로 한 `cudaMemcpyAsync`는 어떻게 동작하나?
→ **pinned 메모리에 있는 내부 스테이징 버퍼를 거쳐서** 전송한다.
그래서 pageable 메모리에서의 전송은 **더 느리고, 비동기성을 깨뜨린다.**

### 해법

```cpp
thrust::universal_host_pinned_vector<float> hprev(height * width);
```

호스트 벡터를 Pinned 메모리에 할당하면 D2H 복사가 **진짜 비동기**가 되어 컴퓨트 연산과 겹친다.
바꾼 뒤 다시 프로파일링해서 device-to-host 복사가 계산과 겹치는지 확인할 것. (연습 02.04.02)

## 8. 핵심 요점

| 언제 쓰나 | 이유 |
|---|---|
| **비동기 프로그래밍 모델** | 메모리 전송을 겹치려고 / CPU와 GPU 계산을 겹치려고 / 다른 GPU 계산과 겹치려고 |
| **CUB** | 비동기 범용 병렬 알고리즘이 필요할 때 |
| **Nsight Systems** | 프로파일링, 최적화 기회 식별, 비동기 실행 시각화 (+ NVTX로 간소화) |
| **`cudaStream_t`** | CPU 및 다른 스트림과의 비동기 실행을 활성화하려고 |
| **`cudaMemcpyAsync`** | 메모리 복사를 CPU 기준 비동기로 만들려고 |
| **Pinned 메모리** | 디바이스에서 **비동기적으로** 복사하려고 / 디바이스에서 **더 빠르게** 복사하려고 |

### 한 줄 흐름

```
Thrust(동기)  →  CUB(비동기) + cudaDeviceSynchronize 위치 조정   … 계산 ↔ IO 겹침 (2배)
              →  cudaStream_t + cudaMemcpyAsync                 … 계산 ↔ 전송 겹침
                 (+ 스테이징 버퍼로 data race 제거)
              →  universal_host_pinned_vector                   … 전송이 진짜 비동기
```
