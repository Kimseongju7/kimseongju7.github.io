**[geul-hub] 발표의 문제 정의를 하나의 인과 사슬로 재구성**

- ✨ 기존 재료의 가장 큰 위험은 "버전 혼란"과 "피드백 확인 부담"을 **나란히 놓인 두 문제처럼 말하게 되는 것**이었다. 그러면 청중이 "버전 문제면 구글 독스 쓰면 되잖아"라고 생각한 채 뒤를 듣게 된다. 그래서 둘을 **증상 → 원인의 사슬 하나**로 묶기로 했다.
- ✨ 사슬의 핵심 고리를 직접 찾아냈다 — **"최종최종"이 생기는 이유는 그때는 진짜 최종이라 믿었는데 아니었기 때문이고, 최종이 아니게 된 이유는 피드백이 또 왔기 때문**이다. 이 인과를 넣으면 파일명 자체가 피드백 루프의 증거물이 되어, 두 문제를 억지로 연결할 필요가 없어진다.
- ✨ 여기에 "피드백은 여러 개이고 카톡·메일·코멘트로 흩어져 온다"를 더해 문제의 단위를 **문서에서 피드백 항목으로 내렸다.** AI가 하는 일(피드백↔반영 연결)의 단위와 일치해서 솔루션 연결이 단단해진다.
- ✨ 최종 구조는 ① 표면 문제(뭐가 진짜 최종인지 모른다) → ② 원인 추적(피드백이 또 왔으니까) → ③ 원인 속 숨은 문제(반영 확인 비용) → ④ 두 해결 대응(쌓임은 버전 관리, 반영 확인은 AI)이 됐다.

**[geul-hub] Design.pdf 3→4페이지 전환 문제 해결**

**[frontend] 발표 질의응답 대비 프론트엔드 학습**

## 배운 것

<!-- claude-recall-learn:rlatjdwn:start -->

**문제는 나란히 놓지 말고 증상 → 원인의 사슬로 묶는다**

- ✨ 문제 두 개를 병렬로 제시하면 청중이 **먼저 떠올린 반박("그건 기존 도구로 되잖아")을 품은 채** 나머지를 듣는다. 설득력은 하나를 증상, 하나를 그 증상을 낳는 원인으로 배치해 사슬을 만들 때 나온다.
- ✨ 해결책을 말할 때도 **두 개를 같은 무게로 말하면 안 된다.** "버전 관리로 해결했다"는 구글 독스도 하는 일이라 거기서 멈추면 "그럼 뭐가 달라?"가 나온다. 기본기는 짧게 치고, 기존 도구가 못 푸는 나머지 반쪽에 시간을 써야 차별점이 선다.

**"최종최종"은 밈이 아니라 피드백 라운드의 기록이다**

- ✨ 파일명이 늘어나는 인과는 이렇다 — "최종"이라 저장한 건 진짜 끝이라 믿었기 때문이고, 끝이 아니게 된 이유는 매번 하나뿐이다: **피드백이 또 왔기 때문.** 따라서 "진짜최종"이 하나 늘 때마다 피드백이 한 바퀴 돌았다는 뜻이다.
- ✨ 이렇게 읽으면 파일명이 **스스로 문제를 증명하는 증거물**이 된다. 두 문제를 억지로 이어 붙일 필요가 없어지고, 청중이 이미 웃으며 공감한 장면이 그대로 논거가 된다.

**기존 솔루션은 먼저 인정한 뒤 "남는 것"으로 좁힌다**

- ✨ "구글 독스로도 해결되긴 한다"를 먼저 인정하는 건 발표에서 오히려 무기가 된다. 심사위원이 반론하기 전에 선점하고, 그 기준에서도 **남는 것**만 남기면 비교가 공정해 보인다.
- ✨ 구글 독스 기준으로 남는 셋: ① **서식** — hwp 원본이 필요한 팀은 애초에 옮겨가지 못한다, ② **화면 분리** — 코멘트와 diff가 다른 화면에 있어 연결은 여전히 사람 머릿속에서 한다, ③ **'해결됨' 체크는 자기 신고** — 사람이 수동으로 누르는 것이라 까먹고 안 고쳐도 체크는 눌린다. 도구는 피드백을 *모아주기만* 하지 *확인해주지는* 않는다.

**새 개념은 단어보다 장면이 먼저다 — 장면 → 질문 → 이름 붙이기**

- ✨ "반영 확인"처럼 청중이 모르는 개념을 **단어로 먼저 던지면 허공에서 떨어진다.** 순서를 뒤집어 ① 장면(피드백이 카톡·메일·코멘트로 흩어져 온다) → ② 질문("내가 받은 피드백 중 뭐가 반영됐고 뭐가 빠졌지?") → ③ 이름 붙이기("저희는 이걸 반영 확인 문제라고 부릅니다")로 가면 개념이 발견되는 형태가 된다.
- ✨ 같은 원리로 **"해결하려고 파고들다 보니 문제가 사실 두 개였다"는 발견의 서사**가 "문제가 두 개 있습니다"라는 선언보다 자연스럽다. 다만 "두 가지 문제"보다 **"성격이 다른 문제 두 개가 섞여 있다"** 가 낫다 — 뒤에서 "첫 번째는 쉽게 풀렸지만 두 번째가 진짜 어려웠다"로 이어갈 수 있기 때문.

**발표에서 단어 하나가 문제의 무게를 결정한다**

- ✨ "더 편리하게 할 방법"이라고 말하는 순간 그때까지 쌓아온 *고통*의 서사가 **불편 개선·있으면 좋은 도구 수준으로 격하된다.** 심사에서 "편의성 개선"과 "문제 해결"은 무게가 다르다.
- ✨ 문장 길이도 마찬가지다. 질문과 발견을 한 복문에 담으면 **발표에서는 끝에 가서 반드시 뭉개진다.** "알게 되어, 그래서…"로 흘리지 말고 "알게 되었습니다."로 끊은 뒤 다음 문장을 시작해야 각각에 힘이 실린다.

**발표 분량은 글자 수로 환산해서 관리한다**

- ✨ 공백 제외 글자 수 기준 **보통 발표 페이스는 분당 250~300자**다. 1,000~1,100자면 3분 30초~4분이고, 긴장해서 빨라지면 3분, 여유 있게 가면 4분 초반으로 잡으면 된다.
- ✨ 그래서 대본을 쓴 뒤에는 **자를 순서를 미리 정해 두는 게 좋다.** 뒤에서 다시 다루는 내용(중복)부터 자르고, 공감을 만드는 장면 묘사는 마지막까지 남긴다.

**우리 프론트엔드를 한 문장으로**

- ✨ **"Next.js 15 App Router + React 19 + TypeScript 기반 SPA로, 백엔드보다 먼저 MSW 가짜 서버를 세워 API 계약대로 UI를 완성한 뒤 환경변수 하나로 실서버에 붙이는 방식"** 으로 개발했다. 서버 상태는 TanStack Query, 클라이언트 상태는 Zustand, 응답은 전부 zod로 런타임 검증한다.
- ✨ 질문이 오면 숫자로 답하기 좋은 규모 감각도 정리해 뒀다 — 프론트엔드 커밋 **141개**(2026-05-30~08-16), `src` 약 **31,000줄 중 테스트가 12,400줄**(테스트 파일 112개 + E2E 3 시나리오), CI 게이트 5단계에 커버리지 임계 **80%**.

## 메모

- **발표자료 PDF가 아직 이전 버전이다.** 어제 고친 HTML에서 다시 뽑아야 한다.
- geul-hub 레포의 **발표설계.md와 발표자료 HTML 두 파일이 미커밋 상태**로 끝났다. (이 볼트가 아니라 geul-hub 쪽)
- 프론트 실제 화면을 보며 설명받는 건 **아직 대기 중**이다. Chrome 확장에 `localhost:3000` 접근을 허용하거나, 직접 클릭하며 "이 화면 뭐야"라고 묻는 두 가지 방법이 있다. mock 모드 dev 서버는 계속 떠 있는 상태.
- 발표 전체가 **10분이면 문제 정의를 2분 30초~3분으로 줄여야** 한다. 자르는 순서는 ① 3페이지 구글 독스 반박 문단 → ② 2페이지 SNS 부분이고, 4페이지 반영 확인 장면 묘사는 남긴다.
- 대본은 6페이지까지 나왔다. 그 뒤 본론 3파트(무엇을 만들었나·어떻게 만들었나·무엇이 남았나)가 통째로 남아 있다.
