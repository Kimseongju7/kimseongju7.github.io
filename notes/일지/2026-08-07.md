- ✨ 라이브 프로브로 새 계약을 확정했다 — 엔드포인트 `openapi.naver.com/v1/search/blog.json` → **`naverapihub.apigw.ntruss.com/search/v1/blog`**, 헤더 `X-Naver-Client-Id/Secret` → **`X-NCP-APIGW-API-KEY-ID` / `X-NCP-APIGW-API-KEY`**, 계정도 네이버 → **NCP 별도 가입**. 반면 쿼리 파라미터·응답 `items[]` 구조·`display` 1–100·`start` 1–1000·**쿼터 25,000회/일은 그대로**라 "키워드당 1,000건 풀 수집이 공짜"라는 설계 전제는 살아남았다.

## 배운 것

<!-- claude-recall-learn:rlatjdwn:start -->
**외부 API 는 한 파일에 격리해 두면 계약이 통째로 바뀌어도 타격이 작다**

- ✨ 네이버 호출이 `src/lib/http-naver-fetcher.ts` 한 파일에 몰려 있고 `NaverFetcher` 인터페이스로 추상화돼 있었던 덕에, **엔드포인트와 인증 헤더가 전부 바뀌었는데도 파싱·집계·xlsx·대시보드 로직은 한 줄도 손대지 않았다.**
- ✨ 테스트가 `FixtureNaverFetcher` 로 돌아가고 있어서 47개 중 실제로 깨진 건 옛 호스트를 단언하던 **1개뿐**이었다. 외부 의존을 인터페이스 뒤에 두면 계약 변경의 폭발 반경이 "그 구현체 하나 + 그걸 단언하는 테스트"로 줄어든다.
- ✨ 그래서 이번엔 아예 **계약 자체를 환경변수로 고르게** 만들었다(`apihub` 기본 / `legacy`). 공급자가 이관 중일 때는 "새 것으로 갈아탄다"보다 "둘 다 가능하게 둔다"가 싸게 먹힌다.

---

**`npm audit` 의 건수는 위험도가 아니다 — 실행 경로를 봐야 한다**

- ✨ 남은 5건은 전부 전이 의존성이었고, 이 앱에는 도달 경로가 없었다 — `postcss` 는 빌드타임에 우리 CSS 만 처리, `sharp` 는 `next/image` 미사용이라 미해당, `uuid` 는 ExcelJS 가 v4 를 `buf` 없이 쓰는 경로라 미해당.
- ✨ 반대로 **패치 비용이 싸면 노출이 낮아도 그냥 올리는 게 맞다** — Next 취약점은 대부분 안 쓰는 기능(이미지 최적화·미들웨어·Server Actions·rewrites)이었지만 15.5.7 → 15.5.22 패치 레벨 업이라 비용이 거의 없었다.
- ✨ **`npm audit fix --force` 는 그냥 돌리면 안 된다.** 이번엔 exceljs 를 3.4.0 으로 되돌리는 breaking downgrade 를 제안했다 — 취약점 숫자는 줄지만 실제로는 손해다.

---

**공급자 공지를 먼저 확인하지 않으면 "정확한 설명"이 통째로 틀린다**

- ✨ developers.naver.com 발급 절차를 자신 있게 안내받았지만, 그 경로는 **7월 31일에 이미 닫혀 있었다.** 문서(README)와 안내가 동시에 틀렸고, 공지 하나로 전부 뒤집혔다.
- ✨ 교훈은 단순하다 — **외부 서비스의 가입·발급·요금 절차는 코드보다 빨리 낡는다.** 캐시된 지식이 아니라 공지·릴리스 노트를 먼저 확인하고, 확인한 날짜와 함께 문서에 남겨야 한다.
