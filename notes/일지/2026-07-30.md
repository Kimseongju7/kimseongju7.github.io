**Flutter 상태관리 선택은 "누가 데이터를 들고 있느냐"의 문제다**

- ✨ setState·Riverpod·BLoC 셋 다 하는 일은 같다 — 데이터가 바뀌면 화면을 다시 그린다. 차이는 **그 데이터의 소유자**다. setState는 위젯이 들고 있어서 화면이 늘 때마다 부모→자식 전달과 콜백 배선을 손으로 해야 하고, Riverpod은 위젯 밖 provider가 들고 있어 화면이 필요한 것만 구독하므로 배선이 사라진다.
- ✨ 그래서 **선택 시점이 늦으면 비싸진다.** 나중에 바꾸면 화면 코드를 전부 다시 쓰고 폴더 구조부터 갈린다. 판단 기준은 "여러 화면이 같은 상태를 공유하는가" 하나로 충분했다 — 하트 아이콘이 세 화면에 나오는 순간 답이 정해졌다.

---

**Firebase 클라이언트 설정 키는 비밀이 아니다 — 서비스 계정 키와 정반대**

- ✨ `firebase_options.dart`·`google-services.json` 안의 API 키는 **보안 규칙에 종속**된다. 규칙이 막으면 아무것도 못 하고, 유출돼도 별 일이 없어서 커밋이 표준 관행이다. 반면 서비스 계정 키는 규칙을 **우회**하므로 유출되면 DB 전체가 장악된다 — 절대 커밋 금지.
- ✨ 근본적으로 앱은 사용자 기기에 설치되므로 그 안의 키는 어차피 추출 가능하다. **숨기는 게 보안이 아니라 Firestore 규칙이 보안**이다. 앱 읽기 권한을 열 때 규칙을 어떻게 쓰느냐가 실제 방어선이다.

---

**"막힌 것"과 "규칙이 막은 것"은 다르다**

- ✨ 인증 없는 쓰기 시도가 `INVALID_ARGUMENT`로 실패했을 때 그걸 "규칙이 거부했다"로 읽으면 **규칙이 비어 있어도 안전하다고 착각**하게 된다. 실제 사유는 예약 ID가 규칙 평가 전에 튕긴 것이었고, 정상 ID로 다시 해야 `PERMISSION_DENIED`가 나왔다.
- ✨ 교훈은 검증 설계 쪽이다 — **실패의 종류를 구분하지 않으면 검증이 아니라 요식행위**가 된다. 그리고 규칙 검증은 반드시 규칙을 우회하지 않는 경로(인증 없는 REST)로 해야 한다. Admin SDK로는 규칙이 있든 없든 성공하기 때문이다.

---

**문서의 예제와 설치된 패키지 버전은 어긋난다**

- ✨ 스킬 문서 예제의 `AsyncValue.valueOrNull`을 그대로 썼더니 컴파일 오류 3건이 났다. 설치된 **Riverpod 3.4.2에는 그 getter가 없고 `value`가 nullable**이었다 — 문서가 2.x 기준이었던 것. 추측으로 고치지 않고 패키지 소스를 직접 열어 확인했다.
- ✨ 서버 작업 때 `python` vs `python3`와 같은 종류의 실패다. **문서는 "보통 그렇다"를 말하고, 컴파일러는 "여기선 아니다"를 말한다.** 그래서 코드를 쌓기 전에 `flutter analyze`를 먼저 돌리는 습관이 값을 한다.

---

**대화형 OAuth 로그인은 자동화가 원천적으로 불가능하다**

- ✨ `firebase login`이 non-interactive 모드에서 실패하는 건 버그가 아니라 설계다. OAuth는 브라우저 리다이렉트가 필수고, 사람이 "이 앱에 권한을 준다"고 직접 클릭해야 하기 때문이다. 그래서 CI에는 `firebase login:ci`로 뽑은 토큰을 환경변수로 넣는 **별도 경로**가 있다.
- ✨ 서버 쪽 서비스 계정 키와 발상이 같다 — **사람 인증을 한 번 해서 기계 인증으로 바꾸는 것.** 한 번 로그인하면 토큰이 파일에 남아 이후는 전부 비대화형으로 돌아가므로, 사람 손이 필요한 건 딱 그 한 번이다.

**CSS에서 디자인 토큰 뽑기 — 색상 개수가 디자인 시스템의 유무를 말해준다**

- ✨ SSUPath CSS에서 hex 색상이 **528개** 나왔다. 토큰이 정의된 디자인 시스템이라면 20~40개면 충분하다. 즉 이 숫자 자체가 시스템이 없다는 증거이고, 빈도 상위와 컴포넌트 셀렉터에서 실제로 쓰이는 것만 골라내는 작업은 **없던 시스템을 만들어 주는 일**이었다.
- ✨ 값 하나에서 질감이 드러나기도 한다 — 그림자가 `0 4px 8px rgba(0,104,143,0.24)`, 즉 `#00688F`라는 **브랜드 색이 섞인 청록 기운의 그림자**였다. 순수 회색으로 바꾸면 느낌이 달라진다. 이런 건 페이지를 마크다운으로 변환하면 전부 사라진다.

---

**남의 디자인 시스템을 이식할 때는 원본 규칙과의 충돌을 명시적으로 처리한다**

- ✨ Linear의 "2차 색상 금지"는 우리 앱의 상태 구분(모집중/종료/마감임박)과 정면 충돌했다. 해결은 원문을 더 읽는 데서 나왔다 — Known Limitations의 "Product UI color tags reside in in-product surfaces only"가 **금지 대상이 마케팅 페이지지 제품 UI가 아님**을 알려줬다. 다만 방식은 원본 정신에 맞춰 바꿨다: 꽉 찬 컬러 pill 대신 작은 색 점 + 중립 텍스트로, 색을 신호로만 쓰고 면적을 주지 않는다.
- ✨ 두 번째 충돌은 **언어**였다. 공격적인 음수 자간(-3.0px)은 라틴 대문자 기준이고, 한글은 자모 간격이 이미 조밀해 음수 트래킹을 주면 글자가 겹친다. Inter에는 한글 자체가 없어 폴백도 필요했다. 서구 디자인 시스템을 그대로 가져오면 **타이포그래피에서 먼저 깨진다**.
