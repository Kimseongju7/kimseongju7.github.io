**[frontend] 로컬 개발 스택 재기동**
- ✨ 작업을 이어가려고 로컬 환경부터 되살렸다. 프론트 dev 서버는 3000 포트에서 `feat/rail-flat` 브랜치를 계속 서빙 중이라 멀쩡했지만 백엔드가 죽어 있었고, 원인은 Docker 데몬 자체가 꺼져 있던 것. Docker Desktop을 먼저 올린 뒤 postgres·kafka·backend 스택을 기동해 localhost:8080 health `UP` 까지 확인했다. 이미지는 지난번 빌드한 최신 develop 그대로 재사용.

**[frontend] 앱 전체 배지·라벨 인벤토리와 리디자인 시안**
- ✨ 배지 문구·색이 제각각이라 코드를 전수 조사해 7종을 표로 정리했다 — `위치 잃음`(노랑) · `수락 대기`/`만료됨`(노랑) · `만든 사람` · `N/M 처리됨` · `처리 중` · 파란 카운터 · 인디고 버전 칩. 각각 어디서 쓰이고 뭐가 문제인지까지 같이 적었다.
- ✨ 스타일 후보를 3안으로 뽑아 실제 맥락(피드백 카드·그룹 멤버·폴더 행)에 얹은 목업 아티팩트를 만들었다 — **B1 소프트 틴트**(무테 + 옅은 면, 의미색을 앱 팔레트 안으로 제한하고 노랑 퇴출), **B2 점 + 평문**(pill을 버리고 색 점 + 회색 글자), **B3 모노톤 미니 태그**(회색으로 통일하고 문제만 빨간 글자). 앞서 만든 F 플랫 레일과 시각 언어가 같다는 이유로 B1을 추천안으로 올렸다. 카운터·버전 칩은 세 안 모두 유지.
- ✨ 문구 개선안은 검토 후 범위를 좁혔다. `수락 대기` · `만료됨` · `N/M 처리됨` 은 현행 유지로 확정했고, 바꿀 후보는 `위치 잃음` 과 `처리 중 → 문서 읽는 중…` 두 건만 남겼다.

**[frontend] orphaned 배지 문구 — 정확성과 신뢰 사이 재설계**
- ✨ `위치 잃음` 을 "본문에서 사라짐"으로 바꾸자는 1안에 제동을 걸었다. `orphaned` 는 문장이 삭제됐다는 뜻이 아니라 **재탐색이 실패했다**는 뜻이라, 문장이 멀쩡히 있는데 매칭이 못 찾은 경우도 포함된다. 시스템이 확신할 수 없는 걸 단정하는 문구라 "위치 찾지 못함"으로 한 차례 수정.
- ✨ 그런데 "못 찾음"은 정직한 대신 **서비스 실패담처럼 읽혀 사용자 신뢰를 깎는다**는 게 다음 지적이었다. 그래서 주어를 바꾸는 프레이밍 4종으로 후보 10안을 뽑았다 — 문서 탓(원문 변경됨 / 원문이 바뀌었어요 / 문서가 많이 바뀜), 사실 서술(이전 버전 기준 / 이전 버전에서 작성 / 원문 위치 바뀜), 해결 유도(다시 연결 필요 / 연결 대기), 상태 서술(위치 미연결 / 위치 연결 없음). 추천은 **"원문 변경됨"** — 매칭 실패의 정당한 함의이면서 짧고, 원인을 문서 변화 쪽에 둔다. 각 후보를 B1 배지 모양으로 렌더하고 트레이드오프도 병기했다.
- ✨ 안내문도 같은 원칙으로 맞추기로 했다. "문서에서 이동할 위치가 없습니다" → "문서가 바뀌어 원래 위치로 이동할 수 없어요. 피드백 연결로 새 위치를 지정할 수 있습니다" 처럼, 상태 서술 뒤에 곧바로 해결 경로를 붙이는 형태.

**[frontend] 피드백 마크가 안 그려지는 버그 추적 (진행 중)**
- ✨ 문구 작업 중 실제 화면에서 ③번 피드백(fb3)의 마크가 안 보이는 걸 발견해 진단에 들어갔다. 서버 기준으로는 fb3이 orphaned가 아니라 **앵커가 살아 있다**고 응답하는데 DOM에는 마크가 0개였고, 같은 문서의 fb1·fb4는 정상 렌더됐다. 즉 특정 조건에서만 걸러진다는 뜻.
- ✨ 주석 생성 로직을 따라가 원인을 좁혔다. 최신 버전에서 마크는 `currentAnchor`(최신 재탐색 좌표)가 있어야 그려지는데, fb3만 그 값이 어긋나 있는 것으로 보인다. 확인 도중 토큰 파일이 정리돼 재발급하고 이어갔다. (오늘 기록은 여기까지 — 원인 확정 전)

## 배운 것

**Claude로 UI 수정할 때는 프로덕트 코드부터 건드리지 말 것**
- 곧바로 프로덕트 코드를 수정하게 시키면 토큰이 많이 들고, 요청 사항이 제대로 반영되지 않거나 내 뜻이 제대로 전해지지 않는 경우가 많았다. 그래서 먼저 **아티팩트로 내 요구사항을 정확히 이해하고 있는지 확인하고, 후보군을 만들어 보라고 시킨 뒤** 구현에 들어갔더니 요구사항대로 정확히, 그리고 토큰도 절약하면서 구현할 수 있었다.

<!-- claude-recall-learn:rlatjdwn:start -->
**상태 배지 마이크로카피 — "정확함"과 "신뢰를 깎지 않음"은 다른 축이다**
- ✨ 상태 문구를 쓸 때 1차 기준은 **시스템이 실제로 아는 것만 말하기**다. `orphaned` 처럼 "삭제됐다"와 "못 찾았다"를 구분할 수 없는 상태에서 "본문에서 사라짐"이라고 쓰면, 시스템이 모르는 사실을 단정하는 거짓말이 된다.
- ✨ 하지만 정확한 문구가 곧 좋은 문구는 아니다. "위치 찾지 못함"은 사실이지만 **서비스가 실패했다는 자백처럼 읽혀** 신뢰를 깎는다. 해법은 거짓말이 아니라 **주어를 바꾸는 것** — 같은 사실을 "시스템이 실패했다" 대신 "문서가 변했다"(원문 변경됨), "기준 시점이 다르다"(이전 버전 기준), "이렇게 하면 된다"(다시 연결 필요)로 서술하면 정직함을 유지하면서 프레임이 달라진다.
- ✨ 그래서 상태 문구 후보를 뽑을 때는 표현을 흩뿌리지 말고 **프레임 축(문서 탓 / 사실 서술 / 해결 유도 / 상태 서술)을 먼저 세우고** 축마다 후보를 채우는 게 낫다. 후보끼리 뭐가 다른지 비교 가능해지고, 트레이드오프도 축 단위로 설명된다.

**디자인 후보는 맥락 위에 얹어야 판단이 된다**
- ✨ 배지 스타일 3안을 빈 화면에 나열하지 않고 실제 사용처(피드백 카드·그룹 멤버·폴더 행) 목업 위에 렌더해 비교했다. 배지는 주변 요소와의 대비로 읽히는 컴포넌트라, 떼어 놓고 보면 셋 다 괜찮아 보이지만 맥락에 얹는 순간 "너무 붙인 느낌"·"노랑이 튄다" 같은 차이가 드러난다.
- ✨ 선택 근거도 미감이 아니라 **기존 결정과의 일관성**에서 나왔다. B1을 민 이유는 예뻐서가 아니라 앞서 만든 F 플랫 레일과 시각 언어(무테 + 옅은 면)가 정확히 같기 때문이다. 이미 내린 결정이 다음 결정의 기준이 되면 앱 전체가 한 덩어리로 보인다.

**앵커 기반 피드백의 렌더 조건**
- ✨ 문서 위 피드백 마크는 "피드백이 존재하면" 그려지는 게 아니라 **최신 재탐색 좌표(`currentAnchor`)가 있어야** 그려진다. 그래서 서버가 앵커를 살아 있다고 응답해도 클라이언트 쪽 좌표가 어긋나면 마크가 조용히 사라진다 — 서버 상태와 화면 상태를 각각 따로 확인해야 원인이 잡히는 구조다.
