## 배운 것

<!-- claude-recall-learn:rlatjdwn:start -->
**HWP 를 브라우저에서 렌더할 때의 제약 — SVG 백엔드와 포매팅 개행**

- ✨ `@rhwp/core` 는 WASM 으로 `HwpDocument` → `renderPageSvg()` / `renderPageHtml()` 렌더와 `getPageTextLayout()`(TextRun 별 위치·글자 좌표 JSON)을 준다. 그런데 **SVG 백엔드를 쓰면 `<text>` 안에 HTML `<mark>` 를 끼워 넣을 수 없어 앵커 하이라이트가 성립하지 않는다** — 하이라이트가 필요한 제품이면 렌더 백엔드 선택이 곧 기능 가능 여부다.
- ✨ 라이브러리가 **가독성 때문에 태그 사이에 넣는 포매팅 개행**이 DOM 에서는 텍스트 노드로 남는다. 사람 눈에는 안 보이지만 런 경계를 넘는 인용 매칭은 이걸 만나면 전부 깨진다. 렌더된 HTML 위에 텍스트 오프셋을 매핑하는 구조라면 반드시 확인할 지점.

---

**변환은 충실도를 만들어내지 않는다 — 같은 엔진이면 결함도 함께 구워진다**

- ✨ "HWP 를 PDF 로 변환해서 보여주면 낫지 않나"는 직관과 달리, **변환기가 같은 rhwp 조판 엔진이면 지금 보이는 제목 잘림·겹침이 그대로 PDF 안에 박힐 뿐이다.** 개선은 없고 변환 시간·메모리, 추출 홉이 하나 늘어 앵커 인용 매칭 드리프트 증가, 한글 폰트 임베딩 문제만 새로 생긴다.
- ✨ 변환이 의미를 갖는 건 **더 충실한 변환기를 쓸 수 있을 때**뿐이다(예: 서버에서 한컴 공식 변환). 즉 "브라우저에서 변환"과 "서버에서 변환"은 같은 아이디어가 아니라 완전히 다른 선택지다.

---

**정보통신망법 제50조의2 — 자동 이메일 수집 자체가 금지 행위**

- ✨ 영리 목적 광고 전송을 위해 **자동 수집 프로그램으로 이메일 주소를 수집하는 행위 자체**가 금지된다(수집·판매·유통 모두). 도구를 만들 수는 있어도 용도가 발송이면 법적 리스크가 실재하므로, 스펙 단계에서 "수집한 이메일을 어디에 쓸 것인가"를 못 박아두는 게 맞다.
- ✨ 반면 블로그 URL 의 ID 에 도메인을 붙이는 `{blogId}@naver.com` 은 페이지에 있는 이메일을 긁는 게 아니라 **"파생"이라 성격이 다르다.** 다만 ID 변경·메일 미개통 케이스가 있어 미검증 값이므로, 실제 발견한 이메일과 컬럼을 분리하거나 `추정` 플래그를 달아야 한다.

---

**네이버 블로그 페이지의 렌더 방식 실측 — 어디까지 plain HTTP 로 되는가**

- ✨ `blog.naver.com/PostView.naver` 와 `m.blog.naver.com/{id}/{logNo}` 는 **서버 렌더링이 끝난 상태**라 plain curl 로 본문을 받을 수 있다. 반면 `blog.naver.com/profile/intro.naver` 는 200 이지만 **소개글이 HTML 에 없고**(보일러플레이트뿐), `m.blog.naver.com/{id}?tab=1` 은 JS 셸이다.
- ✨ 결론은 **프로필을 읽으려면 헤드리스 브라우저가 필요**하고, 그 순간 "plain HTTP 라서 80~130초면 된다"던 서버리스 계산이 무너진다는 것. 아키텍처 결정을 지탱하던 전제일수록 추측하지 말고 실제로 fetch 해 봐야 한다.

---

**서버리스 실행 한도와 "측정하지 않은 리스크"를 구분하기**

- ✨ Vercel `maxDuration` 은 Fluid Compute 기준 Hobby 300초 / Pro 800초(베타 1800초)이고, 2025-04-23 이전 레거시는 Hobby 60초 / Pro 300초다. 또 **Hobby 는 약관상 비영리 전용**이라 용도가 상업적이면 플랜 자체가 걸린다.
- ✨ "네이버가 Vercel IP 를 차단할 것"이라는 리스크는 **실제로 측정한 사실이 아니었다.** 이런 항목은 아키텍처를 뒤집는 근거가 아니라 **10분짜리 스파이크로 측정할 대상**으로 분류해야 한다 — 추측을 제약처럼 다루면 설계가 잘못된 방향으로 굳는다.
- ✨ "로컬 워커 + 클라우드 UI" 조합은 편해 보이지만 실제로는 터널·작업 큐(DB 필수) 중 하나가 반드시 붙어서, **클라우드 제약과 로컬 제약을 둘 다 떠안는** 최악의 조합이 되기 쉽다.

---

**정렬된 결과에서 부분 실패는 결측이 아니라 순위 왜곡**

- ✨ 페이지네이션 일부가 실패하면 빈칸만 생기는 게 아니다. 블로거 시트가 **수집 포스트 수 내림차순**이라, 페이지가 빠진 블로거는 카운트가 낮아져 **순위가 조용히 뒤바뀐다.** 빈칸은 눈에 보이지만 뒤바뀐 순위는 안 보인다 — 그래서 결과물에 키워드별 완전성 메타를 함께 실어야 한다.
- ✨ 같은 맥락에서 하나 더 — **정당화할 수 없는 설정 노브는 장식이다.** "수집 깊이 100/300/500" 옵션은 "왜 300이고 500은 아닌가"를 답할 근거가 없어서 아예 없앴다.
