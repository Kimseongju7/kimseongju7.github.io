## 요약

geul-hub 의 원본 렌더링 브랜치를 검수하고 마감했다. 게이트는 처음부터 전부 초록이었지만, 정작 확인하고 싶었던 시나리오 — 한글·워드를 올리면 서버가 PDF 로 변환해 원본 서식 그대로 보여주는 것 — 이 mock 에 아예 없었다. 변환본을 가진 시드 3건이 전부 원래부터 PDF 라, 변환이 필요한 형식은 한 건도 화면에 없었던 것이다.

그래서 오늘 나온 문제는 대부분 **mock 이 계약과 어긋나 있던 자리**였다. 확장자 목록이 백엔드보다 옛날 것이었고, 스캔 PDF 는 뷰어 PDF 가 연결돼 있지 않아 이미 구현해둔 기능이 화면에서 막혀 있었으며, 목록 카드의 "미리보기 불가" 배지는 판정이 정확히 반대로 뒤집혀 있었다. 그 사이에 진짜 버그도 하나 나왔다 — `pending` 은 시간이 지나면 바뀌는 상태인데 폴링이 없어, 변환이 끝나도 새로고침 전까지 대기 화면에 갇혔다.

프론트에서 못 고치는 두 건은 이슈(#178 백필, #180 목록 필드)로 올렸고, 푸시하려는 시점에 팀원이 이미 둘 다 머지해둔 걸 발견해 리베이스 후 PR #184 로 마감했다. 남은 수동 검수는 백엔드 연동 후로 미뤘다. mock 으로는 "시드에 심어둔 상태가 화면에 제대로 그려지나"까지만 답할 수 있고, 정작 중요한 실제 변환 품질과 앵커 정합은 확인할 방법이 없기 때문이다.

## 배운 것

<!-- claude-recall-learn:rlatjdwn:start -->
**전이 상태에는 폴링이 있어야 한다**

- ✨ `pending` 처럼 **시간이 지나면 저절로 바뀌는 상태**를 받아놓고 다시 물어보지 않으면, 서버가 일을 끝내도 화면은 영원히 대기 화면에 머문다. 상태별로 주기를 정하는 순수 함수(`extractionPollIntervalMs`)로 뽑아두면 `pending` 일 때만 폴링하고 종료 상태에선 끄는 걸 테스트로 고정할 수 있다.

**테스트가 진짜로 그 수정을 지키는지 확인하는 법**

- ✨ 테스트를 쓴 뒤 **고친 코드를 일부러 되돌려 실패하는지 본다.** 폴링 테스트에서 `refetchInterval` 을 빼니 8초 대기 후 실패했고, 그제서야 이 테스트가 빈 테스트가 아니라는 보증이 생겼다. 통과하는 걸 확인하는 것만으로는 아무것도 검증하지 못한 테스트를 걸러낼 수 없다.

**mock 이 계약을 어기면 구현한 기능이 화면에서 막힌다**

- ✨ 시드가 계약과 어긋나 있으면(스캔 PDF 에 뷰어 PDF 미연결) 그 케이스를 노린 구현이 정작 화면에서 안 보이고, 더 나쁜 건 **옛 테스트가 그 위반 상태를 기대값으로 굳혀버린다**는 것이다. 계약대로 시드를 고치면 테스트가 깨지는데, 이때 고쳐야 하는 건 시드가 아니라 테스트다.
- ✨ 반대로 mock 이 못 하는 것도 명확하다. 실제 파일을 파싱하지 않으니 상태값은 "추출해봤더니 없더라"가 아니라 **"없는 걸로 친다"** 로 시드에 선언된 값이다. 그래서 파일 내용과 상태값이 어긋날 수 있고, 일부러 진짜 글자 없는 PDF 를 만들어 둘을 맞춰야 화면이 거짓말을 하지 않는다.

**판정 근거가 없는 UI 표시는 지우는 게 낫다**

- ✨ 파일 확장자로 미리보기 가능 여부를 때려맞추면, 아키텍처가 바뀌는 순간 판정이 **정반대**가 되고 아무도 눈치채지 못한다. 응답에 판정할 데이터가 없다면 근거 없는 표시를 유지하기보다 제거하고, 필요한 필드를 API 에 요청하는 이슈로 분리하는 편이 정직하다.
- ✨ 그 필드가 들어와도 판정은 `hasViewPdf` 하나로 해야 한다. 스캔 PDF 는 `not_extractable` 인데 변환본이 있고, 백필 제외분은 `done` 인데 변환본이 없다 — **추출 상태와 렌더 가능 여부는 별개 축**이다.

**백엔드가 붙으면 사라질 mock 코드는 만들지 않는다**

- ✨ 업로드 경로에 가짜 변환을 재현하면 흐름 전체를 눈으로 볼 수 있지만, 실서버가 붙는 순간 **쓸모가 사라지고 오히려 걷어내야 할 짐**이 된다. 대신 mock 의 한계를 코드 주석으로 명시하고, 비는 커버리지는 상태를 직접 뒤집는 테스트 1건으로 메우는 게 싸다.

**git·PR 실무 세 가지**

- ✨ 리베이스한 브랜치를 올릴 땐 `--force` 대신 **`--force-with-lease`** — 원격이 예상과 다르면 거부되므로 남의 커밋을 날릴 위험이 차단된다.
- ✨ PR 본문에 `이슈: #160` 처럼 적으면 머지해도 이슈가 **안 닫힌다.** `Closes #160, #161` 키워드여야 자동으로 닫힌다.
- ✨ 후속 작업이 직전 PR 에서 고친 파일을 건드린다면 브랜치를 develop 이 아니라 **그 브랜치 위에 스택**으로 따야 한다. develop 에서 따면 수정 이전 코드라 머지할 때 충돌한다.
