## 요약

오빠가 요청한 블로그 수집 프로그램을 완성했다. 처음에는 ncloud 에서 제공하는 API 로 구현했는데, 응답이 통합 검색 결과라 티스토리나 알라딘 같은 외부 게시글이 섞여 들어왔다. 그러다 네이버 블로그의 네트워크 탭에서 블로그 전용 API 를 발견해 갈아끼우니 블로그 게시글만 들어오는 것을 확인했다.

거기에 더해 수집 결과를 Neon Postgres 에 누적하고 회차별로 다시 볼 수 있게 만들었고, 무응답으로 굳던 수집에는 타임아웃·중지·재시도·실패 알림을 붙였다.

## 배운 것

<!-- claude-recall-learn:rlatjdwn:start -->
**네이버의 1000건 벽은 API 의 제약이 아니라 검색 표면 전체의 제약**

- ✨ 세 경로 전부 상한이 같다 — 검색 API `search/v1/blog` 1000, 통합검색 웹 1000, 블로그 전용 `section.blog.naver.com` 1000. 그래서 "API 를 우회하면 더 뽑을 수 있다"는 가정은 성립하지 않는다.
- ✨ 판별의 근거가 된 건 **응답 크기가 세 번 모두 정확히 같았다는 사실**이다. 봇 감지나 UA 필터링이었다면 CAPTCHA 나 에러 페이지가 오지 크기가 바이트 단위로 일치할 수 없다. "차단인가 상한인가"는 이렇게 응답의 결정성으로 가른다.

---

**거친 지표를 정밀한 숫자처럼 제시하면 그 자체가 오류다**

- ✨ 웹 검색 결과를 비교한다며 HTML 을 curl 로 받아 `grep -o 'tistory\.com' | wc -l` 로 센 숫자(392, 252 …)는 **결과 건수가 아니라 문자열 등장 횟수**다. 연관 검색어·썸네일 URL·스크립트 안 데이터·페이지 구조물이 전부 섞이고, 한 결과 항목이 같은 도메인을 여러 번 포함하기도 한다.
- ✨ 비율의 방향성만 읽히는 지표를 표로 그리면 정밀한 값처럼 보인다. 반면 JSON 을 파싱해 항목별 `bloggerlink` 를 센 API 쪽 숫자(96 vs 4, 2 vs 98)는 정확하다. **숫자를 낼 때는 어떻게 셌는지와 그 한계를 함께 적어야 한다.**

---

**서버리스에서 상태를 갖는다는 것 — Neon = 서버리스 Postgres**

- ✨ Vercel 서버리스 함수는 요청마다 파일시스템이 초기화되고 `/tmp` 만 임시로 쓸 수 있어 **SQLite 같은 파일 DB 가 원천적으로 불가능**하다. 외부 호스팅 DB 가 유일한 선택지다.
- ✨ Neon 의 차이 넷 — ①scale-to-zero(5분 유휴 시 컴퓨트 정지 → 과금 0, 대신 콜드스타트 ~500ms), ②스토리지/컴퓨트 분리(그래서 꺼져도 데이터가 남는다), ③copy-on-write 브랜칭(git 처럼 DB 복사, 즉시·용량 안 먹음), ④HTTP 드라이버(서버리스에서 TCP 커넥션 풀 고갈 없음). 방언 없는 순수 Postgres 라 이사도 쉽다.
- ✨ 그 HTTP 드라이버에는 **대화형 트랜잭션이 없다.** 그래서 블로거 → 실행 → 포스트 순서로 넣어, 중간에 실패해도 외래 키가 깨지지 않게 순서로 무결성을 확보해야 한다.
- ✨ 부수적으로 알게 된 것 — Vercel 의 Sensitive 환경변수와 `vercel env pull` 은 양립할 수 없다. Sensitive 는 값 읽기를 막고 pull 은 값을 읽어야 하기 때문. 개인 프로젝트면 Sensitive 를 끄거나, 로컬 `.env.local` 을 손으로 쓰면 된다.

---

**집계값은 저장하지 말고 조회할 때 재계산한다**

- ✨ 포스트 수·최고 순위·매칭 키워드를 행에 박아두면 다음 수집과 어긋나 **드리프트**가 생긴다. 원본(`collected_posts`)만 남기고 조회 시 `array_agg`·집계로 뽑으면 누적 뷰와 회차별 뷰가 같은 원본에서 서로 다른 범위로 자연스럽게 파생된다.
- ✨ 반면 `found_email` 처럼 "한 번 관측하면 사실인 값"은 반대로 **덮어쓰지 않고 보존**해야 한다. 재계산할 것과 보존할 것을 가르는 기준은 "그 값이 조회 범위에 의존하는가"다.

---

**통합 테스트가 프로덕션 DB 를 공유하면 시간이 지나 깨진다**

- ✨ 처음엔 통과했는데 실제 수집 데이터가 쌓이자 상위 N 조회에서 합성 데이터가 밀려나 실패했다. 테스트가 코드 변경 없이 나중에 깨진 것 — 데이터 양에 의존하는 단언은 시한폭탄이다.
- ✨ 고친 방식은 상위 N 대신 **전부 읽고 접두사(`zz-test-`)로 거르기**. 격리된 DB 를 못 쓸 때는 "내 데이터만 골라내는" 필터가 차선이 된다.

---

**조용한 실패가 가장 위험하다**

- ✨ `Referer` 가 빠지면 네이버가 200 + 빈 본문을 준다. 상태 코드만 보면 성공이라 **수집 0건이 조용히 통과**한다. `totalCount` 부재를 fatal 로 올린 이유가 이것이다.
- ✨ `fetch` 는 기본 타임아웃이 없다. 하나가 응답하지 않으면 그 자리에서 영원히 멈추고, 예외도 안 뜨니 재시도 경로로도 못 간다. 끊어야 복구가 시작된다.
- ✨ 에러를 "요청에 실패했습니다" 한 줄로 뭉치면 무응답인지·차단인지·구조 변경인지 구분이 안 돼 손볼 곳을 못 찾는다. 갈래를 나누고 **받은 본문 앞부분을 함께 남기는 것**이 실제로 디버깅을 가능하게 한다.

---

**웹훅 알림 문구는 서버가 만든다**

- ✨ 클라이언트가 보낸 문자열을 그대로 디스코드 웹훅에 흘리면 **아무나 그 라우트를 때려 디스코드에 글을 올릴 수 있다.** 알림 라우트는 이벤트 종류만 받고 문구는 서버에서 조립해야 한다.
- ✨ 웹훅 URL 은 응답에도 오류 메시지에도 싣지 않는다. 그리고 알림 실패가 수집 자체를 깨뜨리지 않게 분리한다 — 부가 기능이 본 기능을 인질로 잡으면 안 된다.

---

**어댑터는 하위 계층을 무지하게 만든다**

- ✨ 데이터 출처를 검색 API 에서 블로그 전용 검색으로 **통째로 갈아치웠는데** aggregate·누적 저장·xlsx 는 한 줄도 안 고쳤다. `SectionFetcher` 가 응답을 기존 `NaverResponse` 모양으로 바꿔주기 때문.
- ✨ 이틀 전 "외부 API 를 인터페이스 뒤에 두면 계약 변경의 폭발 반경이 줄어든다"고 적어둔 게 그대로 회수된 셈이다. 다만 이번엔 폴백을 없애고(`api-contract` 삭제) 새 경로에 전부 걸었다 — **공급자가 이관 중일 땐 둘 다 두고, 확실히 더 나은 경로가 정해지면 하나로 정리한다.**
