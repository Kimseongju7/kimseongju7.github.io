**[geul-hub] 맥미니를 GitHub Actions 셀프호스티드 러너로 등록**

- ✨ Actions 결제 한도에 걸려 GitHub 호스티드 러너에서 job이 시작조차 되지 않았다. 그래서 늘 켜 두는 맥미니를 `geul-hub/geul-hub` 저장소의 셀프호스티드 러너로 등록했다. 이름과 라벨은 `castlewon-macmini`로 정했고, launchd 서비스로 등록해 로그인하면 자동으로 켜지게 했다. 임시 브랜치에서 테스트 워크플로를 돌려 success를 확인한 뒤 브랜치는 지웠다.
- ✨ 러너를 등록했는데도 재실행한 job이 계속 한도에 걸렸다. 워크플로 14개가 전부 `runs-on: ubuntu-latest`로 되어 있었기 때문이다. `runs-on: ${{ vars.RUNNER && fromJSON(vars.RUNNER) || 'ubuntu-latest' }}`로 바꿔, 저장소 변수 `RUNNER` 하나로 호스티드와 맥미니를 오갈 수 있게 했다(PR #330). macOS에서 막히는 단계에는 분기를 넣었다. apt 대신 brew를 쓰고, actionlint 컨테이너 액션은 `docker run`으로 실행한다.
- ✨ 재부팅 뒤 러너가 GitHub에서 계속 `busy=true`로 막혀 있었다. 재시작 전에 끊긴 job을 GitHub이 여전히 실행 중으로 기록하고 있었기 때문이다. `gh run cancel --force`로 강제 취소하고 몇 분 기다리니 풀렸다.

**[geul-hub] 맥미니 러너에서만 나는 CI 오류 4가지 수정**

- ✨ **setup-python 실패**: macOS용 Python 배포본은 `sudo installer -pkg`로 설치되는데, 러너에는 sudo 비밀번호가 없다. 또 setup-python은 macOS에서 tool cache 경로를 `/Users/runner/hostedtoolcache`로 코드에 고정해 두어서 `.env`로 경로를 바꿔도 소용이 없었다. 그래서 python-build-standalone 배포본(3.10.21, 3.12.14)을 그 경로에 미리 넣고 `arm64.complete` 표시 파일을 만들어, 설치 단계 자체를 건너뛰게 했다.
- ✨ **Docker pull/build 실패**: `keychain cannot be accessed` 오류가 났다. Docker 설정의 `credsStore: desktop`이 키체인을 쓰는데, launchd 서비스로 도는 러너 세션은 키체인을 열 수 없다. 러너 전용 `DOCKER_CONFIG`(`~/actions-runner/docker-config`)를 만들어 `.env`에 지정했다. 처음에는 `auths: {}`로 비워 두었는데도 같은 오류가 났고, 더미 인증 항목을 넣어서야 해결됐다.
- ✨ **backend Testcontainers 실패**: 로컬 `localstack/localstack:3.8` 이미지의 entrypoint 파일이 0바이트로 손상되어 있었다(`exec format error`). 이미지를 지우고 다시 받아 해결했다.
- ✨ **성능 검사 `FileExistsError`**: 셀프호스티드 러너는 job 사이에 `/tmp`가 비워지지 않아, 이전 실행이 남긴 출력 폴더와 충돌했다. 출력 경로를 job마다 비워지는 `${{ runner.temp }}`로 바꿨다.

## 배운 것

<!-- claude-recall-learn:castleown:start -->
**셀프호스티드 러너는 호스티드 러너와 전제가 다르다**

- ✨ 호스티드 러너는 job마다 깨끗한 가상머신에서 시작하고 sudo도 비밀번호 없이 쓸 수 있다. 셀프호스티드 러너는 둘 다 아니다. `/tmp`, Docker 이미지, 설치된 도구가 job 사이에 그대로 남는다. 그래서 고정 경로 대신 `${{ runner.temp }}`를 쓰고, 이미지가 손상되거나 폴더가 남아 있을 수 있다는 점까지 의심해야 한다.
- ✨ macOS 러너에서는 `container:` 옵션과 컨테이너 액션을 쓸 수 없다(Linux 전용). `run:` 단계는 Mac 자체에서 실행되므로 필요한 프로그램도 brew로 Mac에 설치해야 한다. Docker는 컨테이너 안에서 도는 단계에만 쓰인다.
- ✨ `runs-on`에 라벨을 여러 개 적으면 "그중 하나"가 아니라 "전부 가진 러너"라는 뜻이다. 호스티드가 막히면 알아서 셀프호스티드로 넘어가는 자동 전환은 없다. 저장소 변수와 `fromJSON`을 쓰는 스위치 방식이 현실적인 대안이다.

**launchd 서비스에서는 macOS 키체인을 열 수 없다**

- ✨ 백그라운드 서비스로 도는 프로세스는 사용자 상호작용이 없는 세션이라 키체인에 접근하지 못한다. Docker의 `credsStore: desktop`처럼 키체인에 의존하는 설정은 터미널에서는 되고 러너에서만 실패한다.
- ✨ 함정이 하나 더 있다. Docker CLI는 config에 인증 항목이 전혀 없으면(`auths: {}`) 기본 자격 증명 저장소를 자동으로 고르고, macOS에서는 `docker-credential-osxkeychain`이 선택된다. 그래서 더미 인증 항목을 넣어 자동 감지를 막아야 한다.
- ✨ 재현할 때 이미지가 이미 로컬에 있으면 pull을 하지 않아 오류가 나지 않는다. 그래서 "로컬에서는 된다"는 결과에 속기 쉽다.

**setup-python의 macOS 동작**

- ✨ setup-python은 macOS에서 `AGENT_TOOLSDIRECTORY`를 `/Users/runner/hostedtoolcache`로 강제로 덮어쓴다. macOS용 Python 배포본은 `.pkg`를 `sudo installer`로 설치한다. 그래서 러너 환경 변수를 바꿔서는 해결되지 않는다.
- ✨ 대신 tool cache 구조(`Python/<버전>/arm64/`와 `arm64.complete`)만 맞춰 두면 캐시로 인식되어 설치를 건너뛴다. sudo 없이 사용자 소유 standalone Python으로 채울 수 있다.

**GitHub Actions 아티팩트와 재실행 동작**

- ✨ 아티팩트는 셀프호스티드 러너를 써도 맥미니가 아니라 GitHub 서버에 올라간다. 용량 한도는 조직 요금제 기준이라 저장소에 남은 양이 적어도(0.3MB) 쿼터에 걸릴 수 있다. 사용량은 6~12시간마다 다시 계산된다.
- ✨ 결과물이 선택 사항인 업로드 스텝에는 `continue-on-error: true`가 적절하다. 반대로 다음 job이 받아 쓰는 업로드에는 붙이면 안 된다. 실패가 조용히 넘어가면 잘못된 입력으로 배포될 수 있다.
- ✨ Re-run은 실패했던 커밋의 워크플로 파일을 그대로 다시 실행한다. 워크플로나 develop의 수정을 반영하려면 새 커밋을 올리거나 PR 브랜치를 갱신해야 한다(`gh pr update-branch`).

**E2E 실패는 "회귀냐, 의도된 UI 변경이냐" 판별이 먼저다**

- ✨ 버튼이 "사라진" 게 아니라 상호작용 뒤(카드 펼침)로 이동한 것일 수 있다 — 실패한 E2E가 옛 UI를 전제하고 있는지 먼저 확인해야 잘못된 방향(버튼 복원)으로 고치지 않는다. 단언도 UI 의미에 맞춰 바꿔야 한다: "카드가 사라짐" 대신 "처리 집계가 늘고 처리 버튼이 사라짐"처럼, 새 UI에서 그 행위가 실제로 남기는 흔적을 검증한다.

**로컬 E2E 실패의 환경성 판별 절차**

- ✨ 워커를 1개로 줄여도 재현되면 병렬성 플레이크가 아니고, 같은 커밋이 CI에서 통과하면 코드가 아니라 로컬 환경 문제로 분리할 수 있다. 이번 건은 콜드 dev 서버 첫 진입의 `net::ERR_ABORTED`였는데, CI(셀프호스티드) 통과로 추적을 끊었다. 또 GitHub에서 이슈 코멘트를 달 때마다 `issue_comment` 트리거 워크플로가 깨어나 skipped 런 기록이 남는다 — 빈 런은 실패도 수정도 아니다.
