## 배운 것

<!-- claude-recall-learn:rlatjdwn:start -->
**전역 `fetch` 를 인스턴스 메서드로 부르면 안 되는 이유**

- ✨ 클래스에 `fetchImpl` 로 주입해두고 `this.fetchImpl(...)` 로 호출하면 `fetch` 의 `this` 가 window 가 아니라 그 인스턴스가 된다. 브라우저는 여기서 `Illegal invocation` 을 던지고, Node 는 이 제약이 없어 **서버에서만 멀쩡히 동작한다.** 테스트 주입용으로 fetch 를 받는 패턴을 쓸 때는 `(...a) => fetch(...a)` 처럼 감싸서 부르는 게 안전하다.

**조용한 실패는 버그가 아니라 버그 증폭기**

- ✨ 위의 `Illegal invocation` 은 `catch { return null }` 이 통째로 삼켰다. 결과가 "이메일 못 찾음"과 구분되지 않아 전원 null 이어도 아무도 몰랐다. 실패를 삼키더라도 **최소한 경고는 남겨야** 전멸(100% 실패)과 정상적인 빈 결과를 구분할 수 있다.

**서버리스 요청 본문 상한과 청크 분할**

- ✨ Vercel 서버리스 함수는 요청 본문 4.5MB 가 상한이고, 이걸 넘기면 **라우트 앞단이 413 을 내서 핸들러가 아예 실행되지 않는다.** 서버 로그가 비어 있으면 코드 안이 아니라 그 앞을 의심해야 한다.
- ✨ 청크로 나눠 보낼 때는 참조 무결성이 핵심이다. 각 청크가 자기 자식 레코드가 가리키는 부모를 함께 싣게 하면 ⓐ 중간에 실패해도 참조가 깨지지 않고 ⓑ 청크가 자기 자식 수보다 많은 부모를 참조할 수 없어 **크기 상한이 데이터 분포와 무관하게 결정된다.** 부모는 upsert 라 중복 전송돼도 행이 늘지 않는다.
- ✨ 그리고 반쯤 찬 상태는 실패보다 나쁘다 — 중간 청크가 실패하면 회차째 롤백해야 "온전한 수집인 척하는 반쪽 데이터"가 안 남는다.

**HTTP 200 인데 오류인 응답**

- ✨ 네이버 section API 는 실패해도 200 으로 오고, `)]}'` 프리픽스 뒤 JSON 안에 `result.code: "error"` 로 알려준다. 상태 코드만 보면 성공으로 착각한다.
- ✨ 여기서 배운 두 가지. ⓐ **파싱을 재시도 블록 안에 넣어야 한다** — 밖에 두면 파싱 단계 오류가 재시도 경로를 그냥 지나친다. ⓑ **fatal 기준은 "다시 물어보면 답이 달라질 수 있는가"** 다. 서버가 스스로 알려주는 일시적 오류는 재시도·건너뛰기 대상이고, 응답 구조 자체가 어긋난 건 재시도해도 같으니 fatal 이다.
- ✨ 오류 메시지에는 추측이 아니라 서버가 준 원문을 싣는다. "Referer 가 막혔거나 구조가 바뀌었습니다"처럼 지어낸 원인은 둘 다 틀렸을 때 디버깅을 정반대로 끌고 간다. 위치도 `start=211` 같은 내부 값 대신 사람이 읽는 단위("리뷰 · 8페이지")로.

**계속 진행하는 에러 처리에는 폭주 방지가 따라와야 한다**

- ✨ fatal 을 떼고 "실패해도 계속"으로 바꾸면, IP 차단처럼 전부 실패하는 상황에서 남은 요청을 끝까지 두드려 상황을 악화시킨다. **연속 N회 실패 시 중단** 같은 브레이크를 같이 넣고, 멈춰도 모은 결과는 남기고, 자동 중단과 사용자 중지를 화면에서 구분해줘야 한다.

**페이싱은 루프가 아니라 네트워크 계층에**

- ✨ 요청 간 대기(150ms)를 반복 루프에 넣었더니 대시보드 테스트가 31명 × 150ms 를 **실제로 기다려** 타임아웃 직전까지 갔다. 페이싱을 fetcher 안으로 옮기니 스텁을 주입한 테스트에서는 자연히 0 이 됐다 — 대기는 네트워크의 성질이지 루프의 성질이 아니다.

**HTML 에서 이메일 뽑을 땐 태그를 먼저 제거한다**

- ✨ 태그가 붙은 채로 이메일 정규식을 돌리면 프로필 이미지 URL 이 `a@b.png` 처럼 이메일로 잡힌다. 태그 제거 → 텍스트만 → 정규식 순서로. 반대로 `@` 뒤에 `도메인.TLD` 를 요구하는 정규식이면 인스타 핸들이나 멘션은 걸리지 않는다.

**크롬 비밀번호 자동완성의 생체 인증**

- ✨ 자동완성마다 Touch ID 를 묻는 주체는 macOS 키체인일 수도, 크롬 자체 비밀번호 관리자일 수도 있어 구분이 필요하다. 크롬 쪽은 `chrome://password-manager/settings` 의 **"비밀번호 입력 시 화면 잠금 사용"**, macOS 쪽은 시스템 설정 → Touch ID 및 암호의 "암호 자동 완성". 크롬 쪽을 끄면 맥이 열려 있는 동안 누구나 저장된 비밀번호를 채울 수 있으니 화면 잠금(Ctrl+Cmd+Q) 습관이 대신 필요하다.
