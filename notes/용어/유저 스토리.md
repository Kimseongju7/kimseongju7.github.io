## 한 줄 정의
User Story — 기능을 기능 명세가 아니라 **"누가, 무엇을, 왜"라는 사용자 관점의 한 문장**으로 적은 요구사항 단위.

## 자세히
표준 형식은 이렇다.

> **As a** \<누가\> **, I want** \<무엇을\> **, so that** \<왜\>
> (한국어로는 "\<누가\>로서, \<왜\>하기 위해, \<무엇을\> 하고 싶다")

기능 명세("할 일 추가 API를 만든다")와 결정적으로 다른 지점은 **so that(왜)** 절이다. 이 한 조각이 있으면 "이 기능을 왜 만드는지"가 요구사항 자체에 붙어 다니고, 구현 중에 더 나은 방법이 보이면 목적을 유지한 채 수단을 바꿀 수 있다. 반대로 명세만 있으면 목적을 잃은 채 명세만 충실히 구현하는 일이 생긴다.

스토리는 **대화의 약속**이지 계약서가 아니다. 애자일에서 스토리를 "카드 한 장 크기"로 쓰는 이유는 문서로 모든 걸 전달하려는 시도를 포기하고, 대신 만들기 직전에 대화로 세부를 채우기 위해서다. 그 대화의 결과가 [[AC 트리|인수 조건(AC)]]으로 붙는다. 스토리 = 무엇을·왜, AC = 무엇이 되면 완료. 둘은 항상 짝이다.

좋은 스토리의 관용적 체크리스트는 **INVEST**다.

| 글자 | 뜻 |
|---|---|
| **I**ndependent | 다른 스토리와 독립적으로 개발 가능 |
| **N**egotiable | 세부는 협의 여지 있음 (계약서 아님) |
| **V**aluable | 사용자에게 가치가 있음 |
| **E**stimable | 크기를 가늠할 수 있음 |
| **S**mall | 한 스프린트 안에 끝날 크기 |
| **T**estable | 검증 가능 (= AC를 쓸 수 있음) |

흔한 실수는 스토리에 **개발 작업**을 적는 것이다. "DB 스키마를 만든다"는 스토리가 아니라 태스크다. 사용자가 그걸로 무엇을 할 수 있게 되는지가 없기 때문이다. 스토리 하나는 그 자체로 사용자에게 전달 가능한 얇은 조각이어야 한다.

[[PRD]]가 제품 전체의 "왜/무엇"을 담는다면, 스토리는 그 범위를 사용자가 체감하는 단위로 쪼갠 것이고, [[AC 트리]]는 그 스토리를 기계가 판정 가능한 조건으로 다시 쪼갠 것이다. 이 세 층이 이어져야 [[결정화]]가 완성된다.

## 예시
```
✗  "할 일 저장용 JSON 스키마를 정의한다"
   → 태스크. 사용자 가치 없음

○  개발자로서, 흐름이 끊기지 않게 하기 위해,
   터미널에서 바로 할 일을 기록하고 싶다.

   AC:
   - todo add "리뷰 남기기" 실행 시 0.1초 내 프롬프트 복귀
   - 재실행 없이 연속 추가 가능
   - 빈 문자열이면 에러 메시지 + exit code 1
```
INVEST 점검: 독립 ○ / 협의 가능 ○ / 가치 ○ / 추정 가능 ○ / 작음 ○ / 검증 가능 ○ (AC 3개)
