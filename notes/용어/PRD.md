## 한 줄 정의
제품 요구사항 문서 — **"왜 만드는가, 누구를 위한 것인가, 무엇을 만들고 무엇은 안 만드는가"**를 한 곳에 못 박아 두는 기획 문서.

## 자세히
PRD의 목적은 스펙을 빠짐없이 나열하는 게 아니라 **합의를 만드는 것**이다. 같은 기능을 두고 기획·개발·디자인이 서로 다른 그림을 그리고 있으면 구현 단계에서 반드시 충돌한다. PRD는 그 그림을 문장으로 꺼내 놓아, 만들기 전에 어긋남을 발견하게 한다.

핵심 구성은 대체로 다음과 같다.

| 항목 | 내용 |
|---|---|
| **배경 / 문제** | 지금 무엇이 불편한가([[pain-point]]) |
| **목표 / 성공 지표** | 무엇이 되면 성공인가 (측정 가능하게) |
| **대상 사용자** | 누가 쓰나, 어떤 상황에서 |
| **범위(Scope)** | 이번에 만드는 것 |
| **비범위(Non-goals)** | **이번에 안 만드는 것** |
| **주요 시나리오** | 사용자가 실제로 거치는 흐름 |
| **제약** | 기술·일정·법적 제약 |

실무에서 가장 자주 빠지고 가장 비싸게 청구되는 항목이 **비범위(Non-goals)**다. "안 만든다"를 안 적으면 개발 중에 "이것도 되겠죠?"가 계속 들어오고, 범위는 조용히 부풀어 오른다. [[YAGNI]]를 문서 층위에서 강제하는 장치라고 봐도 된다.

또 하나 흔한 실패는 PRD에 **해법을 적어버리는 것**이다. "Redis로 캐싱한다"는 PRD가 아니라 설계 결정이다. PRD는 "목록 조회가 200ms 이내여야 한다"까지만 쓰고, 어떻게 달성할지는 설계 문서와 [[결정 기록]]에 맡긴다. 문제와 해법을 섞으면 나중에 더 나은 해법이 나와도 문서가 그것을 막는다.

PRD는 한 번 쓰고 끝나는 문서가 아니다. [[소크라테스 인터뷰]]처럼 캐물어 가정을 드러내고, 그 결과를 [[유저 스토리]]와 [[AC 트리]]로 내려보내면서 계속 조여 간다. PRD → 스토리/AC → 설계 → ERD 순서가 표준적인 흐름이고, [[우로보로스 사용법|Ouroboros]]에서는 `/ouroboros:pm`이 인터뷰로 PRD를 뽑아낸 뒤 [[Seed 스펙]]으로 [[결정화]]한다.

## 예시
```markdown
# PRD — 로컬 할 일 관리 CLI

## 문제
터미널에서 작업하다 떠오른 할 일을 적으려면 브라우저/앱으로 이동해야 해서
흐름이 끊긴다.

## 목표
- 터미널을 벗어나지 않고 3초 안에 할 일을 기록
- 성공 지표: 기록 1건당 소요 시간 < 3초

## 대상 사용자
터미널 상주 개발자. 단일 사용자, 개인 기기.

## 범위
- 추가 / 목록 조회 / 완료 처리
- 로컬 JSON 파일 저장

## 비범위 (이번에 안 함)
- 팀 공유, 동기화, 서버
- 마감일·알림·반복 일정
- TUI (플레인 출력만)

## 제약
- 외부 DB 의존성 없음, Python 3.12+
```

## 관련
- [[유저 스토리]] — PRD의 범위를 사용자 관점 문장으로 쪼갠 다음 단계
- [[AC 트리]] — 그 스토리를 검증 가능한 완료 조건으로 만든 것
- [[시스템 설계 문서]] — PRD의 "무엇을"을 "어떻게"로 옮기는 다음 문서
- [[ERD]] — 무엇을 저장할지 확정하는 데이터 모델 문서
- [[결정 기록]] — PRD가 다루지 않는 "왜 그 해법을 골랐나"를 담는 문서(ADR)
- [[MVP|MVP (Minimum Viable Product)]] — 범위/비범위를 가르는 기준
- [[pain-point]] — PRD의 출발점인 문제 정의
- [[YAGNI]] — 비범위를 명시하는 습관의 근거
- [[결정화]] — PRD의 애매한 문장을 고정 명세로 굳히는 과정
- [[명세 주도 개발|명세 주도 개발(SDD)]] — PRD를 문서 한 장이 아니라 진실의 소스로 두는 개발 방식
