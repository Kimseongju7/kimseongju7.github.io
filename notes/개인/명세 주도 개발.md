**SDD(Spec-Driven Development, 명세 주도 개발)** 는 구조화된 명세를 진실의 소스로 두고 코드를 그 명세의 산출물로 취급하는 개발 방식이다. 문서를 코드에 맞춰 나중에 갱신하는 게 아니라, 명세를 먼저 고치고 코드가 따라오게 만든다. 방향을 뒤집는 것이 전부인데, 그 뒤집기가 AI 코딩에서 유독 크게 작동한다.

## 왜 지금 이 이야기가 나오는가

병목이 옮겨갔기 때문이다.

에이전트가 코드를 쓰기 전에는 "구현하는 데 걸리는 시간"이 비용의 대부분이었다. 요구사항이 좀 흐려도 사람이 만들면서 알아서 메웠고, 애매한 지점은 구현하다 막히는 순간 자연스럽게 질문으로 올라왔다. 지금은 다르다. 구현은 몇 분 만에 나오고, 흐린 요구사항은 질문으로 올라오는 대신 **모델이 조용히 채워 넣는다**. 그리고 그 추측은 매번 다르다.

즉 실패가 출력이 아니라 **입력**에서 난다. "로그인 기능 만들어줘"는 사람 머릿속에서는 완결된 그림이지만 문장으로 나오는 순간 정보 대부분이 떨어져 나간다. 소셜 로그인이 필요한지, 세션은 몇 분인지, 실패하면 어떻게 되는지 — 말한 적이 없으니 모델이 채운다. 같은 프롬프트를 두 번 넣어도 결과가 다른 이유가 이것이다. 이 문제를 명시적인 산출물로 끌어내는 과정이 [[결정화]]이고, SDD는 그 결정화를 개발 프로세스의 1급 단계로 승격시킨 방법론이다.

## 핵심 주장은 하나다

> 유지보수의 대상은 코드가 아니라 명세다.

이 문장이 SDD의 전부라고 봐도 된다. 따라오는 성질들이 있다.

- **재생 가능성** — 명세가 고정돼 있으면 같은 명세로 다시 실행해 결과를 비교할 수 있다.
- **드리프트 측정** — "지금 만들어진 게 원래 의도와 얼마나 어긋났나"를 판단할 기준점이 생긴다. 즉흥 프롬프트만으로 굴리면 어긋난 건지 원래 그런 건지 알 근거 자체가 없다.
- **검증 가능성** — 완료 판단을 주관이 아니라 합의된 문장([[AC 트리]])에 맡길 수 있다.
- **인계 가능성** — 사람이든 다른 에이전트든, 채팅 로그가 아니라 문서를 넘기면 된다.

반대로 SDD가 **아닌 것**도 분명하다. 문서를 많이 쓰는 것이 SDD가 아니다. 핵심은 분량이 아니라 **가정을 드러내 합의로 바꾸는 것**이다. 결정화되지 않은 요구사항은 문서가 길어도 여전히 액체다.

## 표준 워크플로

도구마다 이름은 달라도 흐름은 거의 같은 곳으로 수렴했다. GitHub의 [Spec Kit](https://github.com/github/spec-kit)을 기준으로 보면 이렇다.

| 단계 | 명령 | 하는 일 |
|---|---|---|
| 0 | `/speckit.constitution` | 프로젝트 원칙·개발 가이드라인 확정 (전 단계에 걸리는 상위 규약) |
| 1 | `/speckit.specify` | **무엇을** 만들지 — 요구사항과 [[유저 스토리]] |
| 1.5 | `/speckit.clarify` | 덜 정해진 부분을 캐물어 채움 (plan 이전 권장) |
| 2 | `/speckit.plan` | **어떻게** 만들지 — 기술 스택과 구현 계획 |
| 3 | `/speckit.tasks` | 실행 가능한 태스크 목록으로 분해 |
| 4 | `/speckit.implement` | 계획대로 실행 |
| 4.5 | `/speckit.analyze` | 산출물 간 정합성·커버리지 교차 검사 |

여기서 눈여겨볼 지점은 두 개다.

첫째, **"무엇을"과 "어떻게"가 분리돼 있다.** `specify`에 "Redis로 캐싱한다"를 쓰면 안 된다. 그건 설계 결정이지 요구사항이 아니다. [[PRD]]는 "목록 조회가 200ms 이내"까지만 쓰고, 달성 방법은 [[시스템 설계 문서]]와 [[결정 기록]]에 맡긴다. 둘을 섞으면 나중에 더 나은 해법이 나와도 문서가 그것을 막는다.

둘째, **`clarify`와 `analyze`가 선택 단계로 붙어 있다.** 실제로 품질을 가르는 건 이 두 개다. `clarify`는 흐린 요구사항이 구현까지 흘러가는 걸 막고, `analyze`는 스펙·계획·태스크가 서로 어긋난 채로 실행되는 걸 막는다. 이 두 단계를 건너뛴 SDD는 사실상 문서를 한 번 더 쓴 바이브 코딩이다.

## 문서 세트는 결국 이 순서다

이름은 도구마다 다르지만 실제로 만들어지는 문서 체인은 거의 고정돼 있다.

```
문제 정의        →  PRD          →  유저 스토리  →  AC 트리
(pain-point)       (무엇을/왜)      (누가/왜)       (완료 조건)
                                                       ↓
                     ERD  ←  시스템 설계 문서  ←  구현 계획
                   (데이터)     (어떻게)            (태스크)
```

각 단계는 앞 단계를 **더 검증 가능하게** 만드는 방향으로만 내려간다. [[PRD]]의 "빠른 조회"는 [[유저 스토리]]에서 "누가 어떤 상황에서"로 좁혀지고, [[AC 트리]]에서 "POST /login 하면 200과 세션 쿠키"로 굳는다. 이 사다리가 끊기면 — 예컨대 PRD에서 바로 구현으로 뛰면 — 검증 기준이 없어서 완료 판정이 다시 주관으로 돌아간다.

실무에서 가장 자주 빠지고 가장 비싸게 청구되는 항목은 **비범위(Non-goals)** 다. "안 만든다"를 안 적으면 구현 중에 "이것도 되겠죠?"가 계속 들어오고 범위는 조용히 부푼다. [[YAGNI]]를 문서 층위에서 강제하는 장치가 비범위 항목이고, [[MVP]]를 실제로 지켜내는 유일한 방법이기도 하다.

## 도구 지형 (2026년 중반)

2026년 현재는 사실상 모든 주요 AI 코딩 도구가 자기 방식의 SDD를 붙였다. 성격이 갈리는 축은 **"명세를 어디에 두느냐"** 다.

| 도구 | 성격 | 명세의 위치 |
|---|---|---|
| **GitHub Spec Kit** | 오픈소스 CLI + 템플릿·프롬프트. 30개 이상 에이전트 지원 | 리포 안 마크다운 |
| **AWS Kiro** | SDD를 중심에 둔 에이전틱 IDE. 모델 자동 라우팅 | IDE가 관리하는 스펙 파일 |
| **[[bmad-method\|BMAD-METHOD]]** | 규모 적응형 애자일 프레임워크. PM·아키텍트 등 역할 에이전트 | 워크플로 산출물 문서 |
| **[[ouroboros-agent-os\|Ouroboros]]** | 로컬 우선 Agent OS. 인터뷰 → 결정화 → 실행 → 평가 → 진화 | 불변 YAML [[Seed 스펙]] + 원장(ledger) |
| **OpenSpec / Tessl 등** | 명세를 검증 가능한 계약으로 다루는 쪽 | 별도 명세 포맷 |

Spec Kit은 **가장 가볍고 이식성이 높다.** 리포 안에 마크다운으로 남으니 도구를 갈아타도 문서가 살아남는다. Ouroboros는 반대로 **가장 강하게 잠근다** — Seed가 불변이라 실행 중에 스펙이 흔들리지 않고, 고쳐야 하면 수정 대신 `evolve`로 새 세대를 파생시킨다. 세대 간 계보가 남아서 되감기가 되는 게 이 방식의 값어치다. 어느 쪽이 맞는지는 프로젝트 수명이 정한다. 한 번 만들고 끝날 것에 불변 명세와 원장은 과하고, 반년 굴릴 것에 마크다운 몇 장은 얇다.

## 실패 모드

SDD가 잘 안 되는 방식은 대체로 넷이다.

**1. 스펙 드리프트.** 가장 흔하고 가장 치명적이다. 코드는 굴러가는데 명세는 안 따라가고, 어긋남이 비싸질 때까지 보이지 않는다. 이 상태가 되면 에이전트가 실제 동작과 충돌하는 출력을 내기 시작하고, 팀은 결국 바이브 코딩으로 돌아간다. 유일한 대응은 규율이다 — **구현 중 스펙의 구멍을 발견하면 코드가 아니라 스펙을 먼저 고친다.** 문서를 죽이는 드리프트의 방향을 뒤집는 게 이 규칙 하나다.

**2. 과형식화 = 워터폴 회귀.** 스펙을 지나치게 굳히면 변경과 피드백 주기가 느려진다. 초기 워터폴에서 겪었던 그 문제다. SDD는 "코드 쓰기 전에 다 정한다"가 아니라 "**추측으로 채워질 자리를 없앤다**"에 가깝다. 아직 모르는 건 모른다고 적는 게 맞고, 그걸 미리 정해버리는 순간 문서가 학습을 막는다.

**3. 컨텍스트 폭발.** 명세가 커지면 에이전트가 리포 전체를 한 번에 추론해야 하고, 컨텍스트가 차면서 출력 품질이 떨어진다. 명세를 기능 단위로 쪼개고, 실행 시점에 필요한 조각만 넣는 설계가 필요하다. [[headroom-context-compression|컨텍스트 압축]] 같은 접근이 붙는 지점이 여기다.

**4. 명세는 있는데 검증이 없음.** "괜찮아 보임"은 검증이 아니다. AC가 모호하면 채점도 모호하다. Ouroboros가 기계적 → 의미적 → 다중 모델 합의 3단으로 평가를 쌓는 것도, Spec Kit이 `analyze`와 `checklist`를 따로 두는 것도 같은 이유다. 결국 **AC 품질이 곧 결과 품질**이다.

## 어디까지 적용할까

전부에 적용하면 망한다. 규모에 맞춰 깊이를 조절하는 게 정답이고, BMAD가 "스케일 적응형"을 내세우는 이유이기도 하다. 대략의 기준은 이렇다.

- **오타 수정·한 줄 변경** — 명세 불필요. 그냥 고친다.
- **단일 기능, 하루 안에 끝나는 것** — AC 몇 줄이면 충분하다. PRD까지 갈 필요 없다.
- **여러 파일에 걸치는 기능** — PRD 없이 유저 스토리 + AC + 간단한 계획.
- **새 시스템, 여러 사람이 붙는 것** — 전체 체인. PRD → 스토리 → AC → 설계 → ERD.
- **에이전트에 위임해 오래 돌릴 것** — 여기서부터는 불변 명세와 평가 게이트가 값을 한다.

판단 기준은 하나로 줄일 수 있다. **"내가 자리를 비운 사이 이게 잘못될 수 있나?"** 그렇다면 명세를 쓰고, 아니라면 쓰지 않는다.

## 정리

SDD는 새로운 발명이 아니다. 요구사항 문서, 인수 조건, 설계 문서는 전부 오래된 물건이다. 달라진 건 **그 문서들의 독자가 사람에서 에이전트로 바뀌었다는 것**이고, 에이전트는 문서의 빈칸을 사람처럼 "일단 물어보는" 대신 조용히 채운다는 것이다.

그래서 SDD의 실질은 문서화 규율이 아니라 **빈칸 관리**다. 어디가 비었는지 드러내고, 비어 있어도 되는 곳과 아닌 곳을 가르고, 채운 결정을 되짚을 수 있게 남긴다. 이걸 하면 도구가 무엇이든 SDD를 하는 것이고, 안 하면 템플릿을 아무리 채워도 문서 있는 바이브 코딩이다.
